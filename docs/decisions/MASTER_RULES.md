# ERP V2 — MASTER DEVELOPMENT, PRODUCTION SAFETY & EXECUTION RULES

> Эзэн 2026-11-10-нд баталсан. ERP V2 төслийн бүх хөгжүүлэлт, бүх модуль, бүх агент, бүх үе шатанд хүчинтэй.
> Эдгээр дүрмийг алгасах, өөрчлөх, өөрийнхөөрөө тайлбарлан зөрчихийг хориглоно.
> Энэ файл нь өмнөх `RULES.md`-г орлоно. Хоёр дүрэм зөрчилдвөл **илүү хатуу** нь хүчинтэй.

## 1. ТӨСЛИЙН ҮНДСЭН НӨХЦӨЛ
Одоогийн ERP нь Cloud.mn сервер дээр Docker Compose ашиглан ажилладаг.
Бизнесийн бодит үйл ажиллагаанд дараах мэдээлэл идэвхтэй ашиглагдаж байна:
- 1,000,000 бодит захиалга
- 100+ жолоочийн мэдээлэл, тооцоо
- Агуулахын үлдэгдэл
- Санхүү, нягтлан бодох бүртгэл
- 5,000+ барааны бүртгэл
- Бараа бүрийн код, нэр, зураг

ERP V2 нь одоогийн ERP-ээс тусдаа шинэ систем болж хөгжүүлэгдэнэ.
Хэрэглэгч программчлалын мэдлэггүй. Код гараар засах, файл хуулж байрлуулах, migration гараар хийх, терминалын команд ажиллуулах заавар өгөхийг хориглоно.
Хөгжүүлэлтийн үндсэн зорилго: одоогийн бизнесийн хэрэгтэй бүх ажиллагааг хадгалж, илүү ойлгомжтой, хурдан, найдвартай, автомат, ажилтнуудад ашиглахад хялбар ERP бүтээх.

## 2. ХУУЧИН СИСТЕМ БА БОДИТ ӨГӨГДЛИЙН ХАМГААЛАЛТ
ERP V2 нь тусдаа repository, тусдаа database, тусдаа environment, тусдаа deployment орчинтой байна.
V2 хөгжүүлэлтийн явцад хуучин системийн production орчинд өөрчлөлт хийхгүй.

Хатуу хориглох үйлдлүүд:
- Production database reset хийхгүй.
- Бодит хүснэгт, багана устгахгүй.
- TRUNCATE, DROP зэрэг destructive үйлдэл хийхгүй.
- Бодит өгөгдлийг seed-ээр дарж бичихгүй.
- Хуучин системийн API болон бизнес логикийг зөвшөөрөлгүй өөрчлөхгүй.
- V2 хөгжүүлэлтийн явцад хуучин production database-д холбогдохгүй.
- Бодит өгөгдөлд зөвшөөрөлгүй migration хийхгүй.

Хуучин ERP-ээс V2 руу өгөгдөл шилжүүлэх ажлыг тусдаа үе шат гэж үзнэ. Шилжүүлэхээс өмнө:
- Өгөгдлийн бүтэц, талбаруудыг судлах.
- Барааны кодын давхардлыг шалгах.
- Барааны нэр, зураг, зургийн холбоосыг шалгах.
- Захиалгын өгөгдлийн бүрэн бүтэн байдлыг шалгах.
- Үлдэгдлийн тооцоог тулгах.
- Туршилтын database дээр migration хийх.
- Backup болон буцаах төлөвлөгөө гаргах.
- Хэрэглэгчээс зөвшөөрөл авах.

## 3. ERP V2-ИЙН ХӨГЖҮҮЛЭЛТИЙН ХАТУУ ДҮРЭМ
Нэг дор бүх ERP-ийг хөгжүүлэхийг хориглоно. Нэг удаад нэг модуль дээр ажиллана.
Модуль бүрийн өмнө дараах дарааллыг заавал мөрдөнө:
1. Одоогийн системийн холбогдох код, API, database model-ийг судлах.
2. Тухайн модулийн бизнес логикийг ойлгох.
3. Хэрэглэгчийн бодит ажиллагааг тодруулах.
4. Тодорхойгүй зүйлсийг хэрэглэгчээс асуух.
5. Одоогийн ажиллагааг хэрхэн хадгалахыг тайлбарлах.
6. Илүү хялбар, цөөн алхамтай хувилбар санал болгох.
7. Бусад модультай ямар холбоотойг тодорхойлох.
8. Болзошгүй эрсдэлийг тайлбарлах.
9. Тестийн төлөвлөгөө гаргах.
10. Хэрэгжүүлэх төлөвлөгөөг хэрэглэгчээр батлуулах.

Хэрэглэгч тодорхой зөвшөөрөөгүй бол код бичихгүй.
"Ойлголоо", "санал болгож байна", "үргэлжлүүлье" гэх ерөнхий хариултыг тухайн модулийн код бичих зөвшөөрөл гэж үзэхгүй.

## 4. БИЗНЕС ЛОГИКИЙГ ХЯЛБАРЧЛАХ
Хуучин системийн бүх логикийг шууд хуулж болохгүй. Модуль бүр дээр дараах асуултыг авч үзнэ:
- Ажилтан одоо энэ ажлыг яаж хийдэг вэ?
- Хэдэн алхам шаарддаг вэ?
- Ямар мэдээллийг давхар оруулдаг вэ?
- Ямар үйлдлийг автоматжуулж болох вэ?
- Ямар алдаа хамгийн их гардаг вэ?
- Илүү энгийн хувилбар байна уу?
- Энэ өөрчлөлт бусад модульд нөлөөлөх үү?

Одоогийн ажиллагааг хадгалах болон илүү хялбар болгох хувилбаруудыг харьцуулж хэрэглэгчтэй ярилцана.
Хэрэглэгчийн зөвшөөрөлгүйгээр бизнесийн дүрэм өөрчлөхгүй.

## 5. МОДУЛЬ ХООРОНДЫН УЯЛДАА
Үндсэн модулиуд: Бараа, Захиалга, Агуулах, Агуулахын хүлээлцэх, Жолооч, Хүргэлт, Санхүү, Нягтлан, Цалин, Нийлүүлэгч, Тайлан, Хэрэглэгчийн эрх, Тохиргоо.

Нэг модулийн өөрчлөлт дараах мэдээлэлд нөлөөлөх эсэхийг заавал шалгана:
- Барааны нийт үлдэгдэл
- Агуулах тус бүрийн үлдэгдэл
- Нөөцлөгдсөн бараа
- Жолоочийн эзэмшилд байгаа бараа
- Хүргэлтэд гарсан бараа
- Буцаагдсан бараа
- Захиалгын төлөв
- Орлого, зарлага
- Өр авлага
- Жолоочийн тооцоо
- Цалингийн тооцоо

Нэг модулийн өөрчлөлтөөс болж өөр модулийн өгөгдөл буруу болохоос сэргийлнэ.

## 6. БАРАА, АГУУЛАХ, ҮЛДЭГДЛИЙН ОНЦГОЙ ХАМГААЛАЛТ
Барааны үлдэгдэл нь ERP-ийн хамгийн чухал хэсэг. Үлдэгдэл өөрчлөх бүх үйлдлийг нэг стандарт логикоор зохицуулах архитектур боловсруулна.

Тус бүрээр нь шалгах үйлдлүүд: бараа орлого авах; бараа зарлага гаргах; захиалгаар бараа нөөцлөх; захиалга цуцлах; агуулах хооронд шилжүүлэх; жолоочид бараа хүлээлгэх; жолооч хүргэлт хийх; жолооч бараа буцаах; бараа гэмтэх, хорогдох; үлдэгдэл засах.

Заавал тестлэх эрсдэл: давхар хасалт; давхар нэмэлт; сөрөг үлдэгдэл; давхар API хүсэлт; нэг үйлдлийг дахин гүйцэтгэх; хоёр ажилтан зэрэг бараа зарлагадах; захиалга цуцалсны дараах үлдэгдэл; хүргэлт буцаагдсаны дараах үлдэгдэл.

Үлдэгдэлд нөлөөлөх үйлдэл бүрийг transaction болон idempotency-ээр хамгаалах боломжийг судалж, архитектурыг батлуулна.

## 7. META CONVERSIONS API — ЗААВАЛ ХАДГАЛАХ
Facebook Boost болон Messenger Chatbot хуудсууд ERP V2-ийн үндсэн системд орохгүй.
Гэхдээ захиалга үүсэх үед Meta Conversions API руу Purchase event илгээх логик хэрэгтэй хэвээр байна. Одоогийн системд энэ нь `app/api/orders/route.ts` болон `lib/meta-capi.ts` файлуудаар ажилладаг.

ERP V2 дээр:
- Purchase event илгээх боломжийг хадгална.
- Давхар event илгээхээс хамгаална.
- Event ID, value, currency мэдээллийг зөв дамжуулна.
- Pixel ID болон Access Token-ийг аюулгүй хадгална.
- Алдаа гарсан event-ийг дахин илгээх боломжийг судална.
- CAPI-г Boost болон Chatbot интерфейсээс хамааралгүй байлгана.

## 8. DATABASE БА MIGRATION
> ⚠️ Хөгжүүлэлтийн үеийн database болон өгөгдлийн асуудлаар `DATA_MIGRATION_DECISION.md` давуу хүчинтэй.

### 8.1 Database ба өгөгдлийн эцсийн шийдвэр (эзэн 2026-11-10-нд батлав)
- ERP V2-ийн бүх модуль, функц, тест бүрэн дуусаж, эзэн **эцсийн зөвшөөрлөө** өгөх хүртэл зөвхөн **хуурамч тестийн өгөгдөл** ашиглана.
- **Хуурамч тестийн өгөгдөл** гэдэгт дараах хоёр хоёулаа багтана:
  - Систем автоматаар үүсгэсэн dummy өгөгдөл, жишээ нь 1,000,000+ захиалгын ачааллын тест.
  - Эзэн болон ажилтнуудын V2 дээр **гараар зохиож оруулсан** тестийн захиалга, бараа, жолооч гэх мэт. Эдгээрийг бодит захиалга авч байгаа мэтээр туршихад ашиглана.
- Хуучин production database-д холбогдохгүй, бодит өгөгдөл татахгүй, импорт хийхгүй.
- Бодит өгөгдлийн шилжилтийг зөвхөн эзний эцсийн зөвшөөрлийн дараа, `DATA_MIGRATION_DECISION.md`-ийн §3-т заасан 8 алхмаар хийнэ.
Migration бүрийг урьдчилан тайлбарлаж, хэрэглэгчийн зөвшөөрөл авна.
- Migration-ийг эхлээд тусдаа туршилтын database дээр ажиллуулна.
- Production-д destructive migration хийхгүй.
- Өгөгдлийн нийцэл, давхардал, үлдэгдлийн тооцоог шалгана.
- Backup болон rollback төлөвлөгөөгүй migration хийхгүй.
- Шаардлагагүй schema өөрчлөлт хийхгүй.
- Бодит өгөгдлийг seed-ээр дарж бичихгүй.

Шинэ системийн schema-г зөв зохион байгуулж болно. Гэхдээ өгөгдөл шилжүүлэх үед хуучин өгөгдлийн утга, холбоос, зураг, кодыг алдахгүй.

## 9. PERFORMANCE БА ОЛОН ХЭРЭГЛЭГЧИЙН АЧААЛАЛ
ERP V2 нь 100+ зэрэг хэрэглэгчтэй ажиллах боломжтой архитектуртай байна.
**(R1-ээр чангаруулсан: 1,000,000+ захиалга, 150 зэрэг хэрэглэгчтэй үед аль ч хуудас гацахгүй.)**
- Жагсаалтын API pagination ашиглана.
- Нэг хуудсанд 20–50 мөр харуулна.
- Жагсаалтын API-д хүнд JSON талбаруудыг шаардлагагүй татахгүй.
- Зураг thumbnail болон lazy loading ашиглана.
- Бүтэн зургийг зөвхөн шаардлагатай үед ачаална.
- READ cache ашиглавал холбогдох бүх mutation дээр cache invalidation хийнэ.
- Database query болон index-ийг оновчилно.
- 150 зэрэг хэрэглэгчийн ачааллын тест хийнэ.

- Холбогдох бүх файлыг өөрөө шинэчилнэ.
- Migration шаардлагатай бол өөрөө үүсгэнэ.
- Build болон тестийг өөрөө ажиллуулна.
- Бүх өөрчлөлтийг Git-д commit хийнэ.
- Хэрэглэгчээс код гараар засахыг шаардахгүй.
- Файл хуулж тавих заавар өгөхгүй.
- Хэсэгчилсэн patch-ийг хэрэглэгчээр хэрэгжүүлэхийг шаардахгүй.
- Алдаатай build эсвэл тесттэй ажлыг дууссан гэж тайлагнахгүй.

Өөрчлөлт бүр буцаах боломжтой байна.

## 11. CLOUD.MN DEPLOYMENT
ERP V2-ийн deployment нь Cloud.mn-ийн сервер болон Docker Compose орчинд тохирсон байна.
Хэрэглэгчид аль болох энгийн deployment загвар гаргана: `git pull` → `docker compose up -d --build`.
Гэхдээ эдгээр хоёр команд дангаараа бүх орчинд аюулгүй deploy хийнэ гэж үзэхгүй. Migration, environment validation, backup, health check шаардлагатай бол deployment процесс дотор автомат, найдвартай байдлаар зохицуулна.

Production deploy хийхээс өмнө:
- Build амжилттай байх.
- Тест амжилттай байх.
- Environment тохиргоо шалгагдсан байх.
- Migration баталгаажсан байх.
- Backup болон rollback төлөвлөгөө бэлэн байх.
- Хэрэглэгч production deploy-ийг тусгайлан зөвшөөрсөн байх.

## 14. АЖЛЫГ ҮЕ ШАТТАЙ БАТЛУУЛАХ

## 15. ЭЦСИЙН ҮНДСЭН ЗАРЧИМ
ERP V2-ийн гол зорилго нь зүгээр нэг шинэ дизайнтай ERP бүтээх биш. Бизнесийн бодит ажиллагааг зөв ойлгож, хэрэгтэй боломжуудыг алдахгүй, үлдэгдэл болон санхүүгийн тооцоог найдвартай байлгаж, ажилтнуудын ажлыг хялбарчлах явдал юм.
Хэрэглэгчийн зөвшөөрөлгүйгээр бизнес логик өөрчлөх, код бичих, migration ажиллуулах, production deploy хийхийг хориглоно.

## 16. БИЗНЕСИЙН ДҮРЭМ (эзэн баталсан)

### B1. Захиалгын нас хүргэлт, тооцоонд хамаарахгүй (2026-11-10)
- Жолооч ихэвчлэн өнөөдөр үүссэн захиалгыг маргааш хүргэдэг.
- Гэхдээ **хэзээ ч үүссэн захиалгыг** (өчигдөр, 7 хоногийн өмнө, сарын өмнө) жолооч хугацаа хамаарахгүйгээр хүргэж, **тооцоондоо оруулах боломжтой** байх ёстой.
- Захиалгын үүссэн огноо (`createdAt`) нь жолоочийн хүргэлт, жолоочийн тооцоо, нягтлангийн тооцоог **хязгаарлахгүй, хуваахгүй**.
- Жолоочийн тооцоо болон нягтлангийн тооцоо **нэг ижил дүрмээр** тоологдоно. Хоёр өөр огноо ашиглаж тоо зөрөхийг хориглоно.
- **Тооцооны өдөр = ХҮРГЭСЭН өдөр.** Захиалга хэзээ үүссэн, хэзээ падаанаар авсан нь хамаагүй — жолооч "Хүргэсэн" гэж баталгаажуулсан өдрийн тооцоонд орно (эзэн "хамгийн хялбараар" гэж сонгосон, 2026-11-10). Нягтлангийн модуль дээр нарийвчилж батлуулна.
- Хуучин системийн алдаа: нягтлан `createdAt`-аар, жолооч `assignedDate`-аар тоолдог, жолоочийн орлого ±7 хоногийн цонхоор хязгаарлагддаг — V2-д давтахгүй.
